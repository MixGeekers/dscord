# 发布与验证

DSCord 的发行包含独立源码包、预构建 npm 包和 Linux amd64/arm64 容器镜像。运行依赖由包清单和锁文件记录，部署配置由安装者提供。安装入口见[服务器部署](deploy/README.md)和[npm 安装](deploy/npm.md)。

## 本地检查

在本包目录运行以下命令。

```sh
npm ci --ignore-scripts
npm run check
npm run build
npm run test:browser
```

`check` 包含语法、TypeScript 与模块检查。浏览器检查覆盖聊天界面、独立客户端和管理后台。测试数据采用合成身份和夹具，运行结果以实际执行输出为准。

原生 Bot 接口变更还应运行 `npm run test:kernel-host`，并按变更范围运行 `runtime:native-check`、`runtime:work-check` 和 `runtime:memory-snapshot-check`。这些检查使用安装者指定的兼容 DSH 路径及本地脚本 provider，适合验证工具、恢复、取消和当前上下文投影。兼容基线见[内核运行说明](deploy/kernel-runtime.md)。

## 构建可安装产物

```sh
npm run release:pack
npm run release:verify -- --extract .local/release-unpacked
npm run npm:pack
```

源码包随附文件清单与 SHA-256 校验值。应从提取后的干净目录重新安装依赖并执行检查。npm 包包含运行代码和预构建界面，需要独立验证 CLI 初始化、账号注册、登录、消息和附件传输。包中保留许可证和第三方声明。

发行内容由打包脚本的明确清单控制。个人运行目录、凭据、开发机器路径、内部执行记录和实验报告保存在维护者的本地资料中。

## CI 与版本发布

分支与 PR 的 CI（`ds-group-ci.yml`）保留一个固定的 `Check and build`。普通应用改动执行语法、lint、格式、类型、单元测试和生产构建；纯文档只检查变更链接；网页、原生 Bot、部署与打包改动按路径在同一任务内追加相应验证。工作流始终启动，避免路径过滤使必过检查一直 Pending。完整验证（`ds-group-full.yml`）在每次发版前由发布工作流调用，也可手动触发，包含源码包与 npm 干净安装、amd64/arm64 的 Docker/Compose 部署、独立 DSH 及 Chromium。两者都使用合成账号和本地脚本响应。外部模型服务的行为需要使用其真实配置另行验证。

源码包、npm 包和镜像采用同一发行版本。版本标签必须与包清单和锁文件一致，发布工作流在验证通过后生成对应产物。预发布版本保留 prerelease 标识，npm 使用相应的预发布分发标签。源码、镜像和 registry 的发布回执分别核对。

GitHub 发布流程由 `.github/workflows/ds-group-release.yml` 定义。完整验证只构建一次经过安装检查的 npm tarball，发行任务复用它，通过 npm Trusted Publishing / OIDC 上传并回读完整性，再做公共 registry 的干净安装；需要包维护者先配置一次准确的仓库与工作流绑定。GitHub 资产先在草稿中回读核对后公开。重跑时核对已有 npm 版本、镜像标签与 GitHub 资产，只补缺项，不覆盖同版本的不同内容。具体配置和恢复步骤见[构建与发布](deploy/releasing.md)。

## 真实环境验证

真实模型与设备验证使用操作者明确选择的服务商、模型、账号、端点和数据目录。具体支持能力取决于所选 DSH adapter 与模型，模型选择说明见[配置与迁移](模型配置与迁移.md)。

验证记录应说明实际拓扑、运行版本、输入、工具回执和可见用量。同机进程、容器、模拟浏览器视口、物理跨机器和真实设备各自提供对应范围的证据。一次实验中的模型名称、调用数量和个人权限仅描述该次运行。

问题修复后保留可重复运行的回归检查。向用户说明当前功能边界和可操作的恢复方法，内部逐次测试流水保存在本地开发资料中。
