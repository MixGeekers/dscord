# 从管理面板更新服务器

Compose 包含独立的 `updater` 服务。实例 owner 在管理后台的“服务器更新”中检查版本、安装并重启，查看进度和历史。operator 与 auditor 可以查看，不能执行更新。普通聊天账号没有更新权限。

首次启用需要部署一个包含更新器的 DSCord 发行，使用该发行的 Compose 配置重新启动。更早的发行没有这项服务和维护确认接口，不能只在旧镜像上添加一个按钮。启用后日常更新由面板完成。

## 范围和前提

- 更新 Core、独立管理后台和内置聊天网页，版本保持一致。API-only 模式的外部静态客户端独立更新。
- 中央账号服务器、Synapse、存储网关和反向代理保持原镜像。本流程会短暂停止 Synapse 以制作一致备份，但不升级它。
- 使用 Docker Engine API 1.45 及以上、Compose 的单 Core/单管理服务与 bridge 网络部署。多副本、共享外部写库及必须修改 Compose 结构的发行需要单独迁移。
- 新旧 Bot 节点按协议协商。在线节点必须支持维护确认；旧节点不会被强制中断。先升级这些节点，再安装服务器更新。未结束的运行中或 unknown 任务也会阻止更新。

只有 `updater` 挂载 Docker socket。Core 和管理服务只读取维护信号，管理服务通过内部 Unix socket 请求更新。更新器具备管理 Docker 的权限，部署权限应由实例所有者保管。默认 socket 是 `/var/run/docker.sock`；Rootless Docker 等环境用 `DS_GROUP_DOCKER_SOCKET` 指定宿主上的实际路径。

## 兼容链路与可选版本

更新器验证各发行的更新清单与 SHA-256，根据 `fromVersions` 和相同节点协议计算升级路径。默认选择通往最新可达版本的最短路径上的下一步；例如当前 Alpha 4、发行依次声明 4→5、5→6、6→7 时，可用版本为 Alpha 5，而不会直接尝试 Alpha 7。每次安装只走一步，完成后重新检查；自动安装也遵守维护时段和失败暂停规则。检查和提醒模式不会自动安装。

后台同时显示最新发行、建议路径及当前可直接安装的可选版本。可以选择其中一个版本安装；安装前会重新下载并验证清单。需要中间升级的版本、协议不同的版本和缺失链路不会成为可选安装目标。较新的不兼容发行不会遮住已有的兼容版本。

检查包含最多 10 页、每页 30 条发行记录；超过范围或任一候选清单校验失败时显示检查错误，不使用未经验证的路径。缺少更新清单的发行只能按其部署指南处理。

更新器容器需要使用包含链路修复的 Alpha 7 或更高发行；已有部署单独维护更新器后，可继续让 Core 和管理后台停留在旧版本。更新器不会在应用更新事务中替换自身。旧版后台仍能显示下一步并安装，Alpha 7 后台增加路径和版本选择。

## 更新方式

默认自动检查并提醒，每六小时检查一次。手动模式只在点击时检查；自动模式在配置的时区和维护时段内安装已经声明兼容的版本。支持跨午夜时段，例如 `23` 到 `4`。预发布部署首次检查默认包含预发布，稳定部署默认只看稳定版；之后保留管理员选择。

更新器只从 `MixGeekers/dscord` 的完整 GitHub Release 读取 `server-update.json` 和 `SHA256SUMS`，核对清单哈希并使用清单中的固定 GHCR 镜像摘要。哈希校验依赖所信任的 GitHub 发布源，不代表另外完成了发布者签名验证。没有清单的旧发行、未完成的发行和普通分支提交不会进入更新列表。

发行必须明确列出可升级的来源版本，声明部署契约、节点协议和数据向后兼容性。来源版本或协议不匹配时只显示提示。维护者需在每次发行前验证和维护 `deploy/server-update-policy.json`，不能仅凭版本号推断兼容。

## 安装过程与恢复

1. 下载镜像。下载失败时当前服务继续运行。
2. 进入维护状态，停止接纳新的聊天写入。节点暂停领取新任务，完成正在处理的工作并确认空闲；两分钟内未完成则取消本次更新，恢复接单。
3. 停止 Core、管理服务和 Synapse，备份 Core、Synapse、治理数据，记录 SHA-256。更新器验证其备份挂载与服务的实际数据挂载相同。备份失败时只清理本次不完整的备份，保留失败原因；另外预留恢复状态记录所需的空间，状态写入失败也不阻止尝试启动原容器。
4. 保留原容器，使用新版镜像启动 Core 和管理服务，保留端口、环境、数据挂载和网络。Synapse 使用原容器启动。
5. 核对 Core 与后台的实际版本、维护状态以及 Matrix readiness。检查通过后记录版本并恢复服务，随后清理本次保留的旧容器。

启动检查失败时恢复原容器并保留当前数据。更新器重启也会从持久事务恢复中断的替换。这里不自动把旧数据库备份覆盖回现有数据；涉及不可逆数据迁移的发行不适用。恢复失败时保持维护状态，后台显示“恢复需要处理”，owner 可重试恢复。失败版本暂停自动尝试，owner 可以在处理原因后手动重试。

服务重启期间面板会短暂断开，并自动读取后续状态。备份包括账号凭据、密钥和聊天数据，保存在 `deploy/updater-state/backups/更新ID/`，文件权限受限。中央与远端附件字节的独立备份仍按原部署指南执行。更新备份不会自动轮换；管理员按自己的备份保留策略清理已确认无需保留的目录。

## 后续手动运行 Compose

更新器将当前应用镜像写入 `deploy/updater-state/current.compose.json`。**该文件存在后，每次手动 `up` 都将它作为最后一个 overlay**，否则基础配置可能重新选中旧镜像。已有 HTTPS 与附件存储 overlay 保持原顺序，最后追加它。例如：

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml \
  -f deploy/compose.https.yaml -f deploy/updater-state/current.compose.json \
  up --no-build --detach --wait
```

保留同一 Compose 项目名、`updater-state` 目录及数据卷。更新器自身的镜像由部署者随完整发行维护；它不会在执行应用更新时替换自己。查看更新器日志可用 `docker compose ... logs updater`。手动灾难恢复同时使用匹配的程序、Core/Synapse/治理快照，方法见[部署指南](README.md#备份和恢复)。

## 维护者验证

模块检查包含下载失败、未排空、备份失败、新版不健康、创建后中断、进程重启恢复、权限和维护信号。`node scripts/server-update-smoke.mjs` 使用隔离 Compose 项目、真实应用与 Matrix、合成账号和本地发行源，验证面板请求到真实镜像替换、数据保留、失败回退和更新器重启恢复，不调用模型。

此 smoke 的候选镜像改变版本标识，并注入启动失败；它验证更新机制，不替代具体发行之间的数据迁移验收。新增来源版本之前，需要另外验证该版本真实数据格式与当前版本的兼容性。
